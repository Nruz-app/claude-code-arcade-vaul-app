@AGENTS.md

## Crítico: lee primero la documentación incluida de Next.js

`AGENTS.md` no es texto de relleno. Este proyecto usa **Next.js 16.2.10** (React 19.2), que tiene cambios que rompen compatibilidad respecto a versiones anteriores. Es probable que tu conocimiento previo esté desactualizado para esta versión. **Antes de escribir o modificar cualquier código de Next.js** (routing, obtención de datos, caché, metadata, configuración, componentes de servidor/cliente), lee la guía correspondiente en `node_modules/next/dist/docs/` — la documentación del App Router está en `node_modules/next/dist/docs/01-app/`. Presta atención a los avisos de deprecación en esos documentos.

Casos concretos con los que ya se ha tropezado en este proyecto:

- **`params` en un page es una `Promise`** y hay que hacerle `await` (ver `app/juego/[id]/page.tsx`).
- **`middleware.ts` no existe: se llama `proxy.ts`.** Next 16 renombró la convención y la función se exporta como `proxy`. La documentación pública de Supabase para Next.js todavía dice `middleware.ts`; copiarla tal cual crea un archivo que Next ignora en silencio y la sesión deja de refrescarse. Además, Proxy usa el runtime de **Node.js** por defecto (antes era Edge).
- **`cookies()` es asíncrono** (`await cookies()`), como en `app/lib/supabase/server.ts`.
- **`export const dynamic` ya no aparece** en la tabla de configuración de segmento. No hace falta: usar `cookies()` en un Server Component ya excluye la ruta del prerenderizado, que es lo que mantiene `/salon` siempre fresca.

## Comandos

- `npm run dev` — inicia el servidor de desarrollo (http://localhost:3000)
- `npm run build` — build de producción
- `npm start` — sirve el build de producción
- `npm run lint` — ESLint (configuración flat, `eslint.config.mjs`)
- `npm run format` — Prettier sobre todo el proyecto; `npm run format:check` solo verifica
- `npm test` — Vitest en modo watch; `npm run test:run` hace una pasada y sale
- `npm run db:check` — comprueba que el Supabase del `.env` está en pie y con el esquema aplicado (corre con `node --env-file=.env`, así que sin `.env` no arranca; el detalle está en **Supabase**)

No hay script de `typecheck`, pero `tsconfig.json` ya lleva `noEmit`: **`npx tsc --noEmit` valida los tipos en ~45 s**, bastante menos que un build completo, así que sirve para iterar. El `npm run build` sigue siendo la verificación final, porque además comprueba las convenciones del App Router. `npm run lint` invoca `eslint` sin argumentos, que con la configuración flat recorre todo el proyecto.

Hay un hook `PostToolUse` que pasa Prettier a cada archivo que Claude Code escribe o edita, y además ESLint `--fix` si es JS/TS (`.claude/format-file.sh`). No hace falta formatear a mano lo que acabas de tocar. Vive en `.claude/settings.local.json`, que **está en `.gitignore`**: es configuración personal, así que en una copia nueva del repo puede no existir — ahí el formateo va con `npm run format`.

**Pero no lances `npm run format` antes de un commit.** `npm run format:check` ya falla en unos quince archivos anteriores al hook (`app/page.tsx`, `app/lib/data.ts`, `next.config.ts`, `AGENTS.md`, `demos/Demos.tsx`, las specs 01–03…): el proyecto nunca se ha formateado entero, solo lo que el hook ha ido tocando. Un `format` global reescribe esos quince y ensucia el diff con archivos que no tienen nada que ver con el cambio. Si el hook no está disponible, formatea solo lo tocado: `npx prettier --write <archivo>`. Y **un `format:check` en rojo no significa que hayas roto nada** — comprueba si los archivos que salen son tuyos.

Otros dos hooks, en el mismo sitio, corren las pruebas (ver **Pruebas** más abajo): `.claude/test-file.sh` en `PostToolUse`, con las del archivo tocado, y `.claude/test-suite.sh` en `Stop`, con la suite entera. El segundo solo se ejecuta si en el turno se tocó código JS/TS, cosa que sabe por un testigo que deja el primero en `node_modules/.cache/`; sin esa condición la suite correría también al final de un turno de pura conversación. Si la suite falla, el hook `Stop` devuelve `decision: "block"` y el turno no se cierra — y respeta `stop_hook_active`, que es lo que impide que unas pruebas que no se consigan arreglar bloqueen el turno en bucle.

Ni el hook ni el script llevan la ruta del proyecto escrita a mano: el `command` usa `$CLAUDE_PROJECT_DIR` y el script deriva su raíz de dónde vive él mismo. Es a propósito — con la ruta fija, copiar la carpeta a otra ubicación dejaba el hook apuntando al proyecto viejo y fallando en silencio. Si lo tocas, mantenlo así.

En la misma carpeta hay un cuarto script, `.claude/play-sound.ps1`, el aviso sonoro para los hooks `Stop`/`Notification`. **Está escrito pero sin enganchar a ningún hook, a propósito**: no es código muerto que haya que borrar.

Sobre espacios en blanco: Prettier ya deja **como máximo una línea vacía seguida**, sin espacios ni tabs al final de línea y con un único salto de línea al final del archivo. El hook aplica esa misma limpieza a los archivos que Prettier no sabe parsear (`.sh`, `.ps1`, `.txt`, `.svg`…), saltándose binarios y `.patch`/`.diff`. No hace falta cuidar esto a mano.

Next.js 16 usa **Turbopack** por defecto tanto en `dev` como en `build`; espera el comportamiento y la salida de Turbopack, no de webpack.

Valida los cambios con `npm run test:run`, `npm run lint` y `npm run build` antes de darlos por terminados. Para verificar cambios de UI hay un MCP de Playwright disponible: levanta `npm run dev` y navega a la ruta; las capturas van a `.playwright-screenshots/` (no versionado).

## Pruebas

**Vitest sobre jsdom**, configurado en `vitest.config.mts`. `npm test` lo deja en modo watch; `npm run test:run` hace una pasada y sale (~50 s, 348 pruebas en 8 archivos; `npx vitest run tests/games/snake.test.ts` corre solo una). El archivo de configuración es `.mts` **a propósito**: como `.ts` en un paquete CommonJS, Vite avisa en cada ejecución de que usa sintaxis ESM, y eso sería ruido en cada disparo del hook.

Hoy las pruebas cubren `app/lib/games/`, que es la parte con lógica propia y sin React. Viven en `tests/`, no junto al código, porque el hook las localiza por nombre: `app/lib/games/snake.ts` → `tests/games/snake.test.ts`.

- **`tests/harness/`** es el andamiaje, y es donde está casi toda la miga:
  - `setup.ts` — el `setupFiles` de `vitest.config.mts`, el único de los tres que nadie importa a mano: instala los stubs de canvas y audio (parchean el prototipo, una vez por archivo) y deja el `body` y el registro de audio a cero antes de cada prueba. Un motor nuevo no lo toca; si una prueba se queja de que no hay contexto 2D, es que corre fuera de Vitest.
  - `audio.ts` — lo mismo con el sonido: jsdom trae `HTMLAudioElement` pero `play()`, `pause()` y `load()` son "not implemented" y escupen un error por la consola virtual en cada llamada, que con la suite corriendo en cada guardado sería ruido constante. Además `play()` devuelve `undefined` en vez de una promesa; el stub devuelve una resuelta y anota qué se reprodujo, que es lo que permite afirmar "saltar suena, ahogarse no".
  - `canvas.ts` — jsdom trae `HTMLCanvasElement` pero **no implementa `getContext("2d")`**, y los cinco motores lanzan si les devuelve null, así que sin este stub no se instancia ninguno. Es un `Proxy` que se traga cualquier método de dibujo y cuenta las llamadas. La alternativa era el paquete `canvas`, que compila Cairo en la instalación; aquí no se miran píxeles, se mira el contrato.
  - `reloj.ts` — reemplaza `requestAnimationFrame` por una cola determinista que vacía la prueba, no un temporizador. Es lo que permite comprobar el cap de `dt` y que el tiempo en pausa no cuenta, sin esperas reales.
  - `contrato.ts` — `verificaContrato(nombre, factory)`, la suite compartida: las invariantes de `.claude/skills/nuevo-juego/contrato.md` convertidas en aserciones. Son 27, y se heredan con una línea.
  - `contraste.ts` y `skins.ts` — la segunda suite compartida, `verificaSkins(nombre, factory, ficha)`, que es lo que hizo comprobable la invariante nº 10 («los colores salen del tema»), la única que el contrato reconocía por escrito que nadie podía verificar. Mide el ratio de contraste de WCAG **componiendo el alfa sobre la superficie real** —un `rgba(0,255,136,0.06)` sobre negro es `#00190d`, no verde brillante—, comprueba que los colores de un grupo se distingan, que ningún literal fuera de la paleta llegue al canvas, y que montar sin skin pinte exactamente igual que montar con `"neon"`, comparando la secuencia entera de colores con `Math.random` estabilizado por un LCG. Eso último se apoya en que **el Proxy de `canvas.ts` anota toda asignación a `fillStyle`/`strokeStyle`/`shadowColor`**, que son el 100 % del color porque ningún motor usa gradientes ni patrones.
  - `mando.ts` — la tercera, `verificaMando(nombre, id, factory)`: cruza el `code` que `GAME_TOUCH` declara para cada botón con las teclas que el motor escucha de verdad, despachándolas sobre `window` y mirando si se consumen (`defaultPrevented`). Un `code` mal escrito en el registro es un botón que no hace nada, y no lo pilla ni el compilador —es un `string`— ni nadie mirando la pantalla en un escritorio.
  - `motor.ts` — monta un motor con canvas, reloj y espías de los cuatro callbacks, que es lo que hace el reproductor.

  **Las tres suites compartidas son 35 comprobaciones** (27 + 3 + 5) **y se heredan con tres líneas**: invócalas todas al crear el archivo de pruebas de un motor nuevo.

- **`tests/games/`** — un archivo por motor, que invoca las suites compartidas y añade lo suyo (que CAÍDA y SERPENTINA emiten `onLives(1)`/`onLives(0)`, que BLOQUE BUSTER suelta el listener de puntero y que romper un bloque suena a ladrillo pero no a rebote, que SERPENTINA juega aunque el PNG no cargue, que RANARIA suena al saltar y al ser atropellada pero no al ahogarse), más `registry.test.ts`, que cubre los olvidos típicos al registrar un juego —un id que no está en `GAMES`, un motor sin entrada en `GAME_CONTROLS`, una ficha de skins incompleta y un motor sin mando en `GAME_TOUCH`—, `audio.test.ts`, que es del helper de sonido y no de un motor, y `skins.test.ts`, que además de probar los helpers guarda la **tabla «de oro»**: los literales que cada motor tenía escritos antes de la SPEC 13, copiados a mano y verbosos a propósito. Nada de snapshots ahí, que se regeneran solos y dejarían pasar una regresión sin que nadie se entere. **Son cuatro tablas, no cinco: RANARIA no tiene la suya** —su ficha llegó después, en `36bee45`— así que copiarla del código de hoy no probaría nada; los literales anteriores están en `git show ec6c1ff:app/lib/games/frogger.ts`, y esa tabla es parte de lo que queda pendiente en la memoria de `skin-designer`.

Dos cosas que la suite **no** afirma, para que nadie las "arregle" creyendo que son un descuido: los cinco motores arrancan en estado `"playing"`, así que un `resume()` sobre un motor recién creado sí encola un fotograma —es inalcanzable desde el reproductor, que gatea pausa y reanudación con `started`—; y el `Image` de SERPENTINA nunca carga bajo jsdom, que es justo el caso del fallback que se quiere probar.

La app necesita `.env` (no versionado) con `NEXT_PUBLIC_SUPABASE_URL` y `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Copia `.env.example`; el README explica de dónde salen. `SUPABASE_DB_PASS` aparece en `.env.example` pero **la aplicación no la lee**: es solo para el CLI de Supabase.

Directorios que **no** son código de la app y conviene no tocar ni tomar como ejemplo: `references/` (mockups de diseño y material gráfico, ignorado por ESLint y Prettier), `demos/` (scratch), `.playwright-screenshots/` y `next-home.png`. Nada de `app/` debe importar de `references/`: los assets que use un juego se **copian** a `public/` (así llegó `snake-fruits.png` desde `references/templates/snake-assets/`).

Ojo con qué ignora git aquí, porque no coincide con lo que ignoran ESLint y Prettier: `.gitignore` solo cubre `.playwright-screenshots/` y el contenido de `.playwright-mcp/` (salvo su `.gitkeep`). `references/`, `demos/` y `next-home.png` **no están ignorados** — aparecen como archivos sin seguimiento y entrarían en un commit si haces `git add -A`. Tampoco lo está `bash.exe.stackdump`, un volcado que deja Git Bash al caerse y que no es del proyecto. Selecciona las rutas al hacer commit.

## Skills

Usa siempre `/frontend-design` para diseñar la interfaz de usuario.

`/nuevo-juego` (`.claude/skills/nuevo-juego/`) añade un juego jugable al catálogo: escribe la spec siguiendo el patrón de la 05, para para que la apruebes, y luego implementa el motor contra `GameFactory`, lo registra y escribe sus pruebas en `tests/games/` — el detalle de qué toca y qué no está en **«Juegos reales»**, en Arquitectura. Qué juego portar lo decide el subagente `game-planner`, no la skill. Su `contrato.md` recoge las invariantes que debe cumplir un motor y el porqué de cada una. Es propia del repo, así que **no** entra en `skills-lock.json`.

`/spec-imp-game` (`.claude/skills/spec-imp-game/`) es `/spec-impl` **con el cierre que una spec de juego siempre necesita**: implementa igual y al terminar lanza `skin-designer` y después `mobile-porter`, **uno detrás de otro y nunca a la vez** (dos llamadas en el mismo mensaje se ejecutarían en paralelo, y las skins tienen que estar puestas antes de auditar el móvil). Antes de lanzar nada exige cuatro puertas, y la tercera —que el id esté en `GAME_ENGINES`— es además el detector de «esta spec no era de un juego»: si no registra un motor, se salta los agentes. **No copia a `/spec-impl`: lo lee.** La skill original no es invocable por el modelo (`disable-model-invocation: true`) y está fijada por hash, así que una copia se quedaría vieja en silencio; leer el archivo en cada ejecución es lo único que no se pudre. Como `/nuevo-juego`, es propia del repo y **no** entra en `skills-lock.json`.

`spec` y `spec-impl` están instaladas en el repo (`.claude/skills/`, `.agents/skills/`) y fijadas por hash en `skills-lock.json`. No las edites a mano: se actualizan con `npx skills@latest add Klerith/fernando-skills`.

## Subagentes

Seis, en `.claude/agents/`. Dos **piensan y escriben, pero no implementan**: `game-planner` y `game-jam` no tocan `app/`, y el que implementa por ellos es `/nuevo-juego`. Otros tres **sí escriben en `app/`, y cada uno en un solo archivo**: `skin-designer` en el motor que le toca —una skin es código de dibujo dentro del motor y no existe otro sitio donde pueda vivir, porque el reproductor monta el canvas pero nunca dibuja en él—, `mobile-porter` en `app/globals.css` —un defecto de móvil que se arregla con una media query no da para una spec, y el CSS del portal está todo en ese archivo— y `game-performance-booster` también en el motor que le toca, porque el coste por fotograma es el bucle de dibujo y ahí es donde vive. A cambio los tres tienen el alcance acotado (un motor por invocación; un solo archivo) y deberes de verificación más duros que los de cualquier skill. **Lo que no entre en su archivo no es suyo**: lo dejan escrito en el informe.

El sexto, `security-auditor`, es **el único que escribe y no trabaja sobre un solo archivo**, porque un control de seguridad no vive en uno: la cabecera está en `next.config.ts`, el mensaje en `app/auth/errores.ts`, el privilegio en `supabase/` y la comprobación permanente en `scripts/db-check.mjs`. Paga el permiso igual que los otros tres, pero con **una lista cerrada y escrita de cuatro archivos** —esos cuatro, y `migrations/` con `schema.sql` siempre en el mismo cambio— en vez de con un archivo único. Solo uno de los cuatro está en `app/`. La contrapartida es la misma: **lo que no entre en la lista va al informe**, no al editor.

- **`game-planner`** — decide cuál debería ser el próximo juego del catálogo. Su valor está en su **memoria**, `.claude/memoria/game-planner.md`: una tabla con todo lo propuesto, aceptado, descartado o implementado, con la razón de cada estado. La lee antes de analizar y la actualiza al terminar, y esa es la regla que impide que vuelva a proponer lo mismo cada vez. Si implementas un juego que está ahí como `propuesto`, **cambia su fila a `implementado`** — el agente nunca propone un `implementado`, así que una fila sin actualizar lo hace recomendar un juego que ya existe. Las filas no se borran ni se reescriben: solo cambia la columna `Estado`. Ojo con su propuesta nº 1, **Pipe Mania (`flujo`): es la única que no tiene entrada en `GAMES`**, así que ahí sí hay que crear el id, la ficha del catálogo y su portada `cover-flujo` (acento `magenta`) — es la excepción a «usa el id que ya existe», en «Flujo de trabajo» más abajo. Las otras tres propuestas (`invasores`, `gloton`, `duelo-pixel`) ya están en el catálogo como simuladas.
- **Tres documentos sobre el catálogo, y no todos mandan igual.** `.claude/memoria/game-planner.md` es la **fuente de verdad**: el histórico con el porqué de cada estado. `references/implemented-game/game-suggestions-todo.md` es la lista accionable derivada de ella (qué toca y en qué orden), e `implemented-games.md`, en la misma carpeta, la ficha de lo ya hecho —mecánicas, puntuación y una foto de `game_sessions`—. **Si el TODO y la memoria discrepan, manda la memoria.** Al implementar un juego hay que tocar los tres, y la foto de partidas se refresca consultando Supabase, no a mano.
- **`game-jam`** — convierte un tema libre ("la ranita", "gravedad invertida") en una spec completa en `specs/game-jam/<id>/`. Trabaja **sin supervisión**: no tiene `AskUserQuestion` y no debe terminar con preguntas abiertas, así que cada hueco lo resuelve y lo deja escrito en `05-decisiones.md`. De aquí salió RANARIA.
- **`skin-designer`** — le da a un motor sus tres aspectos (`neon`, `retro`, `clasico`), uno por invocación. También tiene memoria, `.claude/memoria/skin-designer.md`, con los quince pares motor × skin, su estado y el peor contraste medido de cada paleta; se lee antes de auditar y se actualiza al terminar, y las filas nunca se borran. Los cinco motores están implementados en el código, pero **las tres filas de RANARIA siguen marcadas `pendiente` en la memoria**: al retomar skins, mide sus paletas y cierra esas filas antes de dar nada por hecho. **Su regla número uno es que `neon` no se toca** — es el aspecto histórico del portal, y las pruebas comparan la secuencia entera de colores para demostrarlo.
- **`mobile-porter`** — revisa y arregla cómo se ve el portal en un teléfono. **«Móvil» aquí es la web en el navegador del teléfono**: no hay app nativa ni PWA en el repo y el agente no debe añadir una. Audita las siete rutas en cinco viewports (320, 375, 412, 844×390 en horizontal y 1440 como control de no-regresión) con Playwright —que es devDependency, porque **el MCP de Playwright es configuración personal y no está en `.mcp.json`**— y corrige lo que encuentre **solo en `app/globals.css`**. Sus dos reglas duras: **nada de detección de dispositivo en cliente** (desajusta la hidratación, y es la razón de que las SPECS 14/16/17 lo hicieran todo con CSS) y **no inventar breakpoints** — la escala ya existe y tres de sus cortes están medidos (899.98, 420 y el apilado a 400). Su memoria es `.claude/memoria/mobile-porter.md`, una fila por ruta × viewport; hoy están **todas en `pendiente`**, y ahí quedaron anotadas las cinco sospechas de partida (ninguna `env(safe-area-inset-*)` en el archivo, el único `100vh`, el `overflow-x: hidden` del `body` que esconde los desbordamientos, Press Start 2P en mayúsculas y el horizontal, que no ha mirado nadie).
- **`game-performance-booster`** — mide y abarata el coste por fotograma de un motor, uno por invocación. Es el tercero que escribe en `app/`, y **comparte archivo con `skin-designer`**: el reparto es que las paletas y los roles de color son del segundo, y del primero es **solo cómo se llega a pintarlos**. Su regla número uno es **no cambiar lo que se ve** —ni un píxel, ni un color, ni un halo—, así que tiene vetado bajar `shadowBlur`, simplificar formas o saltarse fotogramas; si la única ganancia posible pasa por ahí, la mide y la deja escrita en el informe. Cinco sondas: cuatro deterministas sobre el harness de Vitest (llamadas de dibujo por frame, asignaciones de color por frame, emisiones de callback —que son renders de React— y heap tras 600 fotogramas) y una en Chromium con Playwright, que es **la única que ve el coste de `shadowBlur` y de `save()`/`restore()`**, porque el Proxy de `tests/harness/canvas.ts` se los traga en 0 ms. Deja el presupuesto medido fijado en `tests/harness/rendimiento.ts` (`verificaRendimiento`, la cuarta suite compartida, que **crea él** en su primera invocación) más una línea en `tests/games/<juego>.test.ts`. Su memoria es `.claude/memoria/game-performance-booster.md`, una fila por motor; hoy los **seis están en `pendiente`**, con seis sospechas anotadas sin medir (el laberinto de 868 celdas por frame de `gloton`, los hasta 120 `fillRect` con blur de `bloque-buster`, los once `save()`/`restore()` y el río Bézier de `ranaria`, los arrays por frame de `rocas`, el `ctx.font` ×3 de `caida` y la rejilla con halo de `serpentina`).
- **`security-auditor`** — comprueba que lo que el portal da por seguro lo sigue siendo, **un área por invocación**: `cabeceras`, `acceso`, `base-de-datos`, `cliente`, `secretos` y `dependencias`. Es el cuarto que escribe, con la lista cerrada de arriba. Su valor está en que **no inventa seguridad, verifica la que ya hay**: las SPECS 04, 06, 07, 15, 19, 20 y 22 la pusieron por partes y `references/security/security-checklist.md` fue la única pasada de conjunto, así que un hallazgo suyo es casi siempre una regresión. Su regla número uno es **que la RLS no se relaja nunca** —ni una política borrada, ni una de `insert` en `profiles`, ni `handle_new_user()` pasada a `security invoker`, que rompería el registro—, y su regla número cuatro es que una cabecera se afirma con `curl -I` y no leyendo `next.config.ts`. Tiene vetados `proxy.ts` (que **no autoriza** a propósito: todas las rutas son públicas), la CSP (tiene spec propia) y la puntuación autodeclarada (asumida desde la SPEC 06). Su memoria es `.claude/memoria/security-auditor.md`, una fila por control; hoy los **cuarenta y cuatro están en `pendiente`**, con seis sospechas de partida anotadas sin sondar y los dos falsos verdes conocidos de `db:check` (`0A000` en la llamada RPC y `23503` en el insert anónimo, que fallan por el motivo equivocado).

## Flujo de trabajo: Spec Driven Design

El desarrollo sigue **Spec Driven Design** con las skills `/spec` y `/spec-impl` (de `Klerith/fernando-skills`). Prefiere escribir o refinar una spec antes de implementar funcionalidades.

- Las specs viven en `specs/` numeradas (`01-...md`, `02-...md`, …). `specs/.spec-config.yml` tiene `AutoCreateBranch: true`: `/spec-impl` crea y cambia a la rama `spec-NN-slug` automáticamente.
- `references/templates/` contiene los **mockups originales en JSX/HTML** de los que se portan las pantallas (p. ej. `home.jsx`, `about.jsx`, `salon.jsx`), juegos HTML de ejemplo en `started-games/` y material gráfico (`snake-assets/`). El audio está en `references/mp3/`, un nivel más arriba. Es material de referencia, no código de la app: al portar algo, consúltalo pero escribe el resultado en `app/` con TypeScript y las convenciones de abajo. **Dos juegos tienen sonido, con dos efectos cada uno**: RANARIA (SPEC 11), el salto y el atropello; y BLOQUE BUSTER (SPEC 12), el rebote y el ladrillo. ROCAS, CAÍDA y SERPENTINA son mudos, y `claudecode-finished.mp3` es un sonido de sistema de Claude Code, no de la app.

## Arquitectura

"Arcade Vault" es un portal retro para jugar clásicos arcade y competir por puntuaciones (ver `README.md`). Ya **no** es solo frontend: hay autenticación real con Supabase, cinco juegos reales sobre canvas y las partidas se registran en la base de datos.

**Qué es real y qué sigue siendo mock**, porque conviven:

| Real                                                                                             | Mock                                                                                          |
| ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| Autenticación (Supabase, correo y contraseña)                                                    | El catálogo `GAMES` y `CATS`, en `app/lib/data.ts`                                            |
| Cinco juegos sobre canvas: **ROCAS**, **CAÍDA**, **BLOQUE BUSTER**, **SERPENTINA** y **RANARIA** | Los otros tres (`gloton`, `invasores`, `duelo-pixel`): reproductor simulado con `setInterval` |
| Registro de partidas en `game_sessions`                                                          | El campo `best` de las tarjetas                                                               |
| El Salón de la Fama (`/salon`)                                                                   | El top 10 del detalle `/juego/[id]` (`seededScores`)                                          |
|                                                                                                  | El ticker de actividad y el top de jugadores de la landing                                    |

- **Solo App Router** — todas las rutas viven en `app/`. Rutas actuales: `/` (landing), `/biblioteca` (catálogo con filtros), `/juego/[id]` (detalle), `/juego/[id]/jugar` (reproductor), `/salon` (rankings), `/acerca`, y las de acceso: `/auth` (solo redirige a `/auth/login`), `/auth/login`, `/auth/registro`, `/auth/recuperar`, `/auth/nueva-password` y el Route Handler `/auth/confirmar`. Las cuatro pantallas comparten marco (`app/auth/auth-card.tsx`), traducción de errores (`app/auth/errores.ts`) y, login y registro, los botones de proveedor (`app/auth/botones-oauth.tsx`); el detalle está en `specs/19-pantallas-de-acceso-y-recuperacion.md` y `specs/20-oauth-con-google-y-github.md`. **`/auth/confirmar` sirve a dos flujos** —la recuperación de contraseña y la vuelta de OAuth— porque los dos acaban en el mismo `exchangeCodeForSession`; lo que cambia es el parámetro `destino`, que solo acepta rutas internas.
- **Patrón servidor/cliente**: las páginas que necesitan estado son client components; cuando además necesitan `metadata`, se dividen en un `page.tsx` Server Component contenedor que exporta `metadata` + un `*-client.tsx` con toda la UI (ver `app/biblioteca/`, `app/acerca/` y `app/salon/`). Sigue este patrón para rutas nuevas. `app/salon/page.tsx` va un paso más allá: además de la `metadata`, carga datos en el servidor y se los pasa al cliente como prop inicial.
- **Datos mock centralizados en `app/lib/data.ts`**: catálogo `GAMES` (los `id` son los slugs de las URLs), tipos compartidos (`Game`, `GameColor`, etc.) y datos de la landing. `seededScores(seed)` genera rankings deterministas — mismo seed, mismas filas; lo sigue usando el top del detalle, ya no el Salón.
- **Estado de usuario en `app/lib/user-context.tsx`** (`useUser()`): es una **fachada sobre la sesión de Supabase**. Al montar hace `supabase.auth.getUser()`, resuelve el nombre visible contra `profiles.username` y se suscribe a `onAuthStateChange`. Expone `{ user: { id, name } | null, loading, signOut, saveScore }`. `saveScore()` sigue escribiendo en `localStorage` (`av_scores`) — es lo único que tienen los invitados. La clave `av_user` del auth falso ya no se usa y se borra al arrancar.
- **Juegos reales en `app/lib/games/`**: `types.ts` define el contrato (`GameFactory`, `GameHandle` con `start`/`pause`/`resume`/`end`/`destroy`, y `GameCallbacks` con `onScore`/`onLives`/`onLevel`/`onGameOver`), `registry.ts` mapea el `id` de `GAMES` a cuatro cosas: el motor (`GAME_ENGINES`), las teclas que anuncia el overlay de arranque (`GAME_CONTROLS`), la ficha de skins (`GAME_PALETAS`) y el mando táctil (`GAME_TOUCH`), y hay cinco motores: `asteroids.ts` (ROCAS), `tetris.ts` (CAÍDA), `arkanoid.ts` (BLOQUE BUSTER), `snake.ts` (SERPENTINA) y `frogger.ts` (RANARIA), más `audio.ts`, que es un helper compartido y no un motor. Los controles viven en el registro y no en el motor **a propósito**: son texto de interfaz, y ponerlos ahí evita ampliar el contrato `GameHandle` que fijaron las specs 05 y 06. Antes estaban escritos a mano en el JSX del reproductor, así que los ocho juegos anunciaban los de ROCAS. **El motor no importa React ni toca el DOM fuera del canvas que recibe**, y todo su estado vive en el closure de la factory — nada a nivel de módulo, porque en Next un global sobrevive entre montajes.
- **Lo que el motor tiene que producir al terminar**: `onGameOver` no recibe la puntuación suelta sino un `GameOverSummary` (`score`, `level` alcanzado, `durationMs` **sin contar pausas** y `reason`). Es lo que se registra en Supabase tal cual, y el motor es el único que sabe cuánto se jugó de verdad. `GameOverReason` admite **solo** `"game_over" | "surrender"` —"surrender" es haber pulsado FIN en vez de perder—, y esos dos valores están fijados además por una restricción `check` en `game_sessions`: añadir un tercer motivo obliga a migrar la base, así que los casos raros (por ejemplo llenar el tablero) se tratan como `"game_over"` normal.
- **Añadir un juego es escribir el motor y registrarlo**, y nada más: el reproductor no cambia, ni el contrato de `types.ts`, ni Supabase. El Salón de la Fama tampoco — sus pestañas salen de `GAMES` y `game_id` es texto libre en `game_sessions`, así que un juego con motor aparece en su ranking sin migración ni SQL. Lo hace la skill `/nuevo-juego`, y sus invariantes están en `.claude/skills/nuevo-juego/contrato.md`. Si al portar un juego te ves tocando el reproductor o el contrato, es señal de que el motor está haciendo algo que no le toca.
- **Skins**: `app/lib/games/skins.ts` define `SkinId` (`neon` | `retro` | `clasico`), la forma `FichaDeSkins` y los helpers `conAlfa`, `esSkin` y `paletaDe`. **El skin llega al motor por el tercer parámetro de `GameFactory`**, declarado siempre `skin = "neon"` y nunca `skin?` — con valor por defecto `Function.length` sigue valiendo 2, que es lo que afirma `registry.test.ts`, y montar sin elegir nada pinta exactamente lo de siempre. Cada motor declara su ficha con la paleta neón como fuente del tipo (`keyof typeof PALETA_NEON`), así que a TypeScript no se le escapa un rol sin definir; el modelo es `SKINS_ROCAS` en `asteroids.ts`. Las fichas se registran en `GAME_PALETAS` (`registry.ts`), que es lo que usa el reproductor para decidir si enseñar el selector — **hoy la tienen los cinco motores**, y `registry.test.ts` cruza ese mapa con `GAME_ENGINES` para que registrar un motor sin skins no pase inadvertido. El selector vive **solo en el overlay de arranque**: ahí `start()` todavía no se ha llamado, así que remontar el motor no reinicia nada. La preferencia es global y va en `localStorage` (`av_skin`, vía `app/lib/use-skin.ts`, que usa `useSyncExternalStore` para no desajustar la hidratación). El detalle y el porqué están en `specs/13-skins-de-juego.md`.
- **El mando y la consola**: los cinco juegos se juegan con el dedo y, desde la SPEC 16, también con el ratón. `app/components/mando-tactil.tsx` exporta **dos** componentes, `MandoCruceta` y `MandoAcciones`, que comparten un hook privado `useMando()`; el reproductor monta cada uno en un costado del chasis `.consola` con la pantalla en medio (SPEC 17). Los dos **despachan `KeyboardEvent` sobre `window`** — las mismas teclas que el motor ya escucha. Por eso ninguna de las tres specs del mando tocó `types.ts` ni la lógica de un motor: los cinco generan ellos mismos la repetición al mantener pulsado (`tetris.ts` descarta `e.repeat` y produce su propia cadencia con DAS), así que un `keydown` al apoyar el dedo y un `keyup` al levantarlo es exactamente su entrada esperada. Qué botones tiene cada juego sale de `GAME_TOUCH`; el `code` declarado es el que el motor escucha, y `tests/harness/mando.ts` (`verificaMando`) lo comprueba despachándolo de verdad. **`setPointerCapture` no es opcional**: sin él, deslizar el dedo fuera de un botón mantenido deja la tecla pulsada para siempre. Cada mitad tiene **su propio estado y su propia escucha de `window`** —dos listeners, ningún contexto— y de ahí sale el eco del teclado físico de la SPEC 16: pulsar `←` enciende el botón de la cruceta y `ESPACIO` el A, cada uno en su mitad, filtrando por `code` contra los botones que esa mitad dibuja. **El mando ya no se esconde según el puntero**: se ve siempre, y lo que `@media (pointer: coarse)` decide hoy es la geometría (50/74 px con ratón, 56/76 con el dedo) — sigue siendo **solo CSS**, porque detectar el aparato en cliente desajustaría la hidratación. Por ancho manda otra cosa: bajo 900 px el chasis se apila (pantalla arriba, controles debajo) y bajo 400 las dos mitades se envuelven a dos filas, sin un corte escrito para eso. El HUD se queda fuera del chasis y se compacta por ancho (`max-width: 720px`): se descuadra porque la ventana es estrecha, no por cómo se señala. La única modificación de un motor en las tres specs fue un `pointerdown` en `arkanoid.ts`, porque en táctil `pointermove` no existe hasta que el dedo se desplaza. El detalle está en `specs/14-controles-tactiles-en-movil.md`, `specs/16-apariencia-del-gamepad.md` y `specs/17-consola-con-controles-a-los-lados.md`.
- **Convenciones que comparten los cinco motores**, y que conviene respetar en el sexto: canvas de **800×600** (el reproductor lo fija en el JSX y `.crt-screen` declara `aspect-ratio: 4/3`, así que otra resolución sale deformada); `dt` capado a 50 ms en el bucle y `lastTime = null` al pararlo, para que volver de otra pestaña no teletransporte nada; los callbacks se emiten **solo al cambiar el valor**, salvo en el reinicio, donde se fuerzan los tres para que el HUD no arrastre la partida anterior; la guardia de `end()` es la primera de las dos barreras contra registrar la partida por duplicado en Supabase; `destroy()` **no** emite `onGameOver`, porque desmontar no es terminar; y los colores del tema se copian como literales, porque el canvas no entiende variables CSS. Los juegos sin vidas (CAÍDA, SERPENTINA) emiten `onLives(1)` al empezar y `onLives(0)` al acabar, o el HUD se queda enseñando tres corazones que no existen.
- **Assets de juego en `public/`**: `snake-fruits.png` (la hoja de sprites de las frutas de SERPENTINA), los dos efectos de RANARIA (`rana-salto.mp3` y `rana-choque.mp3`) y los dos de BLOQUE BUSTER (`bloque-rebote.mp3` y `bloque-romper.mp3`). Se referencian con ruta absoluta (`/snake-fruits.png`): las rutas relativas al módulo no funcionan en Next. Los cuatro mp3 **no son copias** de los de `references/mp3/`, sino versiones recortadas, normalizadas a −1 dBFS y pasadas a mono — los originales traían silencio por delante (630 ms el salto de la rana, 183 ms el rebote) y los dos de impacto venían saturados por encima de fondo de escala. Las recetas, con sus medidas, están en `specs/11-audio-ranaria.md` y `specs/12-audio-bloque-buster.md`. **Los cuatro están normalizados al mismo pico a propósito**: así el equilibrio entre los efectos de un juego lo deciden dos constantes de su motor y no cómo se grabó cada muestra. El audio lo dispara el motor con `crearSfx()` (`app/lib/games/audio.ts`), nunca el reproductor. El motor lleva las coordenadas de cada recorte en una tabla tipada dentro del propio archivo; el original (`references/templates/snake-assets/sprites.js`) las publicaba en `window.SPRITE_ATLAS`, que no existe al renderizar en el servidor. **Ojo si reutilizas ese atlas: sus nombres de fruta están desplazados respecto a la imagen** (lo que llama `banana` es la manzana); las coordenadas sí son correctas, y `snake.ts` ya las lleva con los nombres arreglados. `drawFruta()` deja el suavizado activo a propósito: el recorte mide 160 px de alto y se dibuja a 32, y con nearest-neighbor esa reducción de 5× destroza el sprite.
- **`app/juego/[id]/jugar/page.tsx` es un despachador**: si el `id` tiene motor en `GAME_ENGINES` monta el canvas real, si no cae en la simulación. HUD, pausa y modal de fin son los mismos en ambos casos, pero la rama con motor tiene comportamiento propio que conviene no romper al tocar el archivo: canvas fijo de 800×600, la partida no arranca hasta pulsar ESPACIO en un overlay —o tocarlo, en un aparato táctil—, `blur` y `visibilitychange` la pausan solos (sin eso vuelves a una partida a cámara lenta), el `destroy()` del cleanup es lo que impide que queden bucles vivos al navegar, y el registro en Supabase está protegido por doble barrera contra duplicados (la guardia de `end()` en el motor más `registradaRef` aquí). Con motor **y** sesión el modal de fin no pide iniciales: la partida se registra sola con el nombre del perfil; sin sesión, o sin motor, se cae al `saveScore()` de `localStorage`.
- **Estilos**: Tailwind CSS v4 vía `@tailwindcss/postcss` (no hay `tailwind.config.js`; en v4 se configura en CSS). En la práctica casi todo el estilo es **CSS artesanal en `app/globals.css`** (~3450 líneas): tokens del tema en `:root` (`--cyan`, `--magenta`, `--yellow`, `--green`, `--bg`, `--line`…), clases del sistema (`av-*`, `cover-*`, `neon-*`, `.reveal`) y efectos de fondo. Al agregar UI, reutiliza esas clases y variables en vez de utilidades Tailwind sueltas, para mantener la estética consistente.
- **Fuentes**: Press Start 2P (`--font-pixel`, titulares/HUD) y JetBrains Mono (`--font-mono`, cuerpo) cargadas con `next/font/google` en `app/layout.tsx`. El CSS las consume vía `--pixel` y `--mono`.
- **Animación de scroll**: el hook `useReveal()` (`app/lib/use-reveal.ts`) revela elementos `.reveal` al entrar en viewport; el CSS hace la transición.
- **Iconos**: pixel-art en SVG inline en `app/components/pixel-icons.tsx`; la barra de navegación es `app/components/nav.tsx` y se monta en el layout raíz.
- **TypeScript**: modo strict. El alias de importación `@/*` apunta a la raíz del proyecto (p. ej. `@/app/...`).
- **Idioma**: toda la UI, los comentarios del código y las specs están en español. Mantenlo así.

## Supabase

Autenticación y persistencia con `@supabase/ssr`. Hay un servidor MCP de Supabase configurado en `.mcp.json` para consultar el esquema y aplicar migraciones; la URL lleva el `project_ref` fijado, así que apunta siempre al proyecto de este repo, y hay que habilitarlo (`enabledMcpjsonServers` en `.claude/settings.local.json`).

- **Tres clientes, cada uno en su sitio**: `app/lib/supabase/client.ts` (navegador), `app/lib/supabase/server.ts` (Server Components, con `await cookies()`) y el que crea `proxy.ts` sobre `NextRequest`/`NextResponse`. Nunca compartas un cliente entre peticiones: se filtran sesiones.
- **`proxy.ts` (raíz del proyecto)** refresca la cookie de sesión en cada request llamando a `supabase.auth.getUser()`. No autoriza ni redirige: **todas las rutas son públicas**. Implementa `getAll`/`setAll`, y el `setAll` de esta versión recibe un segundo argumento `headers` con las cabeceras anti-caché que hay que aplicar a la respuesta.
- **Esquema versionado en `supabase/migrations/`.** Aplica los archivos en orden de nombre para recrearlo. Hoy: `profiles`, `game_sessions` y la vista `game_leaderboard`.
- **Mudarse a otro proyecto de Supabase: el runbook es `supabase/README.md`.** Seis pasos, y la mitad no son SQL — el `project_ref` vive en **tres** archivos (`.env`, `.env.example` y la URL de `.mcp.json`) y _Confirm email_ se desactiva a mano en el dashboard. El paso 2 es pegar `supabase/schema.sql`, que es el esquema completo de un tirón, **idempotente y no destructivo** (ni un `drop table` ni un `truncate`; ejecutarlo dos veces no da error ni borra filas). `npm run db:check` (`scripts/db-check.mjs`) verifica el resultado con la _publishable key_, así que ve lo mismo que la app con la RLS aplicada, y **distingue «no se puede conectar» de «falta el esquema»** — que es la confusión que costó una tarde cuando el proyecto del plan gratuito desapareció. Habla con PostgREST por `fetch` y no con `@supabase/supabase-js` a propósito: `createClient()` exige un `WebSocket` nativo que no existe hasta Node 22, y aquí corre Node 20.
- **Regla de sincronía `schema.sql` ↔ `migrations/`:** al añadir una migración hay que reflejarla en `supabase/schema.sql` **en el mismo cambio**. Los dos archivos no compiten: `migrations/` es el histórico y dice **por qué** es como es cada objeto (no se toca ni se reescribe); `schema.sql` dice el **qué**, de forma reejecutable, y es lo único que se pega en una mudanza. Si se queda viejo no da error: recrea una base incompleta meses después, con el proyecto original ya perdido.
  - `profiles` — perfil público. El trigger `on_auth_user_created` lo crea al registrarse tomando el nombre de `raw_user_meta_data.username`, en mayúsculas y cortado a 10 caracteres. **El cliente nunca inserta aquí**: basta con pasar `options.data.username` al `signUp`.
  - `game_sessions` — una fila por partida terminada (`score`, `level`, `duration_ms`, `ended_reason`). RLS: lectura pública, inserción solo con `auth.uid() = user_id`, y **sin políticas de `update` ni `delete`**.
  - `game_leaderboard` — vista con la mejor marca de cada jugador por juego (`DISTINCT ON`), creada con **`security_invoker = on`**; sin eso una vista se salta la RLS de las tablas que consulta.
- **Escritura y lectura**: `app/lib/game-sessions.ts` (`saveGameSession()`, se llama sola al terminar una partida con motor) y `app/lib/leaderboard.ts` (`getLeaderboard()`, `getPlayerBest()`). Ninguna lanza excepciones: devuelven un resultado o una lista vacía, para que un fallo de red no rompa la pantalla. Las de `leaderboard.ts` **reciben el cliente de Supabase como argumento** en vez de crearlo: así la misma función sirve al Server Component en la carga inicial de `/salon` y al componente cliente al cambiar de pestaña. Formatean fechas en **UTC** a propósito — con hora local, servidor y navegador discreparían y React avisaría de desajuste de hidratación.
- **Configuración del dashboard que el repo no puede fijar**, cuatro ajustes en pantallas distintas: _Authentication → Sign In / Providers → Email → **Confirm email** desactivado_ —con ella activa, `signUp` no devuelve sesión—; y _Authentication → URL Configuration → **Redirect URLs**_ con `http://localhost:3000/auth/confirmar`, sin la cual Supabase **ignora en silencio** el `redirectTo` de `resetPasswordForEmail` y suelta al usuario en el Site URL, con lo que el enlace del correo llega y funciona pero no lleva a cambiar la contraseña (SPEC 19). Los dos son independientes: la recuperación manda correo aunque _Confirm email_ esté apagado, porque son plantillas distintas. Y un tercero desde la SPEC 20: _Authentication → Sign In / Providers_ con **Google y GitHub** activados y sus Client ID/Secret, que salen de dos aplicaciones OAuth dadas de alta fuera de Supabase (Google Cloud Console y GitHub Developer Settings), las dos apuntando a `https://<project_ref>.supabase.co/auth/v1/callback` — **nunca a `/auth/confirmar`**, que es a donde reenvía Supabase después. Ojo con `external.google: true` de `/auth/v1/settings`: dice que el proveedor está activado, **no** que sus credenciales sirvan. Y un cuarto desde la SPEC 22, que son tres interruptores sin código detrás: _Sign In / Providers → Email_ con **Minimum password length** en **8** y **Leaked password protection** activada, y _Authentication → **Rate Limits**_ con el tope de registros e inicios de sesión por hora y por IP en **10**. Ojo con el primero: el número está también en `app/auth/errores.ts` (`MIN_PASSWORD`) y en la cadena literal del mensaje de error, así que cambiarlo en el dashboard y no en el código deja al usuario leyendo el genérico. El runbook los detalla en el paso 3 de `supabase/README.md` (3a, 3b, 3c y 3d).
- **La puntuación es autodeclarada.** El juego corre en el navegador, así que RLS garantiza _quién_ escribe, no que el dato sea cierto. Asumido a conciencia; no intentes "arreglarlo" con una Server Action, que no cambiaría nada.
